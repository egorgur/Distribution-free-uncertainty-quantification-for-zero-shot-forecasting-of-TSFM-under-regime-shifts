## Модели и библиотеки (проверять актуальные версии и API!)

- Chronos / Chronos-Bolt / Chronos-2 — `chronos-forecasting` (Amazon), веса `amazon/chronos-bolt-*`, `amazon/chronos-2`, `autogluon/chronos-2-small`. Apache-2.0.
  - **Проверено 2026-10-30** (`scripts/check_chronos.py`, chronos-forecasting 2.3.2, torch 2.15 CPU, transformers 5.22, chronos-bolt-small): 9 квантилей 0.1…0.9; патчи по 16 точек, выровнены по правому краю (последний патч кончается в `t`); нормировка по всему контексту; один проход — горизонт до 64 (дальше пакет достраивает авторегрессией — в `src/models.py` запрещено); float32; детерминизм; батч из контекстов разной длины совпадает с вызовами поодиночке (разница 4e-7 std ряда), поэтому S4/S7 окна считаются одним вызовом. ~9 мс на прогноз на CPU (батч 64, L = 512, H = 64).
  - **Chronos-2** (проверено тем же скриптом): только энкодер (12 слоёв у `chronos-2`, 6 у `chronos-2-small`); 21 квантиль 0.01…0.99, обёртка отдаёт те же 9, что у Bolt; один проход — до 1024 шагов; после нормировки применяется arcsinh. `cross_learning` выключен: иначе прогноз окна зависит от соседних рядов в батче. Детерминизм есть; батч совпадает с вызовами поодиночке (1.8e-6 std ряда). Создавать любую модель через `load_forecaster(model_id)`.
  - Выравнивание патчей: изменение длины на `k < 16` меняет только самый старый патч и статистики нормировки. Фон части S7 «длина хвоста» действительно мал (`docs/results/model_comparison.md`). При смене она срабатывает слабее S4, но именно на ней держится S7 (`docs/results/stage4_signals.md`).
  - **Второй компьютер** (2026-11-01): GTX 1070 (8 ГБ, Pascal, sm_61), 12 ядер CPU. torch 2.15.0 с CUDA выпущен только под CUDA 13.2 и 13.4, где Pascal больше не поддерживается. Поэтому здесь стоит torch 2.14.1+cu126 (в сборке есть sm_60, совместимо с sm_61), остальные пакеты — как в `requirements.txt`. `check_chronos` на CPU проходит. Кеш bolt-small воспроизводится при другой версии torch: пересчёт 8 окон отличается от кеша на 2.1e-6 std контекста (порог 1e-4). Этап 4 здесь идёт 9.5 мин против ~28 на ноутбуке. Прогноз bolt-small на CPU — 3.9–4.2 мс (на ноутбуке 10–12.7). Скорость, которую `cache_forecasts` печатает в конце, усреднена по всем ячейкам в `meta.json`, в том числе посчитанным на ноутбуке.
- TimesFM — `timesfm` (Google), `google/timesfm-2.5-200m-pytorch`. 1.0–2.5 — Apache-2.0; веса 3.0 — некоммерческие.
- Moirai — `uni2ts` (Salesforce). CC-BY-NC-4.0 (для учебного исследования допустимо).
- Детекция смены: `ruptures`.
- Бейзлайны/метрики: `statsforecast`, `utilsforecast` (Nixtla) или свои реализации.

## Метрики

**Уточнение на 2026-11-12:** научрук выбрал единую ошибку H1/H3 — MAE относительно ошибки той же модели в устойчивом режиме того же ряда (`правки научрука.md`, `docs/decisions.md`). Пользователь утвердил полный протокол версии 1 — `docs/protocol_h1_h3.md`: пороги по контролю seed 1, 95-й процентиль основной/90-й для чувствительности, восстановление с подтверждением за 64 точки и ограничениями поздних превышений. Принят приближённый эталон drift с явной оговоркой и дополнительным анализом без drift. Реализация находится в `src/evaluation.py`; новые расчёты без инференса моделей — в `results/protocol_h1_h3_v1/`. Ниже отдельно отмечена прежняя реализация и её исторические результаты.

- **Ошибка окна в прежней реализации** (то, с чем сравнивается сигнал): основная — **MASE** медианного прогноза по горизонту; дополнительная — нормированный **CRPS**. Считается задним числом по известному будущему, только для оценки. Отдельно для каждого `H`. Для кривых по d (H1) — отношение к ошибке в устойчивом режиме (`docs/results/stage3_failures.md`), потому что знаменатель MASE меняется с d.
- **Покрытие интервала** — доля факта внутри [q0.1, q0.9]; номинал 80%. Глобальное (все окна) и условное (по `d`, типу, силе).
- **Риск–покрытие / AURC** — сортировка окон по сигналу, отказ от доли самых подозрительных, средняя ошибка на оставшихся; AURC меньше — лучше. Сравнивать со случайным отказом и с оракулом; сводная величина — выигрыш AURC (0 — случайный отказ, 1 — оракул).
- **AUROC / AUPRC** — разделение «10% худших окон» и остальных. Случайный AUROC = 0.5, случайный AUPRC = доля плохих (0.1).
- **Спирмен** — ранговая связь сигнала с ошибкой.
- **Этап B:** F1 с допуском ±δ, задержка обнаружения, доля ложных обрезок.

## Реализация S4, S5 и S7

- S4: прогнозы для каждой `L` → (а) std медиан по `L`, усреднённое по горизонту; (б) среднее по парам `(Lᵢ, Lⱼ)` и квантилям `|q_k(Lᵢ) − q_k(Lⱼ)|`. Нормировка на масштаб контекста.
- S5 (`src/signals.py`, `embedding_shift`; расчёт — `python -m scripts.cache_s5`, → `results/cache/<name>/<модель>/signals/s5.npz`): эмбеддинги 32 патчей основного контекста на выходе энкодера Chronos-Bolt (токен [REG] отброшен). Среднее последних 4 патчей (64 точки) сравнивается с прежними 28: (а) косинусное расстояние между средними; (б) диагональное расстояние Махаланобиса (среднеквадратичное по координатам отклонение в единицах std прежних патчей; полную ковариацию по 28 токенам в 512 измерениях не оценить). В работе это тот же проход энкодера, что и прогноз; модель вызывается заново только потому, что кеш хранит квантили. Проверено: если изменить последнюю точку контекста, 74% изменения входных эмбеддингов приходится на последний патч (остальное — через нормировку по всему контексту).
  - Chronos-2 (`encode_patches` в `Chronos2Forecaster`; `python -m scripts.cache_s5 --model amazon/chronos-2 --device cuda`, 253 с на GTX 1070): то же определение, эмбеддинги 768-мерные, выход 12-го слоя. Внимание двунаправленное, и после патчей контекста и [REG] стоят токены будущего (H / 16 штук), поэтому выход энкодера на патчах контекста зависит от H. S5 считается отдельно для H = 16 и 64, каждый — из прохода прогноза на этот H; в `s5.npz` тогда есть столбец `horizon`. Проверено на 300 окнах: прогноз, посчитанный из того же прохода, совпадает с `predict_quantiles` точно и с кешем до 5.2e-6 std контекста; эмбеддинги не зависят от состава батча (до 6.7e-6); вход энкодера при H = 16 и 64 одинаков, выход различается в среднем на 7% нормы. При полном расчёте `cache_s5` эти сверки повторяет: S5 окна в одиночку против батча — 5.9e-7 медианы; прогноз из прохода против кеша — 2.7e-6 std контекста.
- S7: M возмущений исходного контекста (шум `N(0, (α·σ_diff)²)`, α ≈ 0.05–0.1; изменение длины хвоста: начало окна сдвигается на несколько точек, конец `t` фиксирован, т. е. `L ± k`, `k ≪ L`) → та же мера расхождения, что в S4. Прогноз всегда начинается с `t + 1`, поэтому прогнозы сравнимы напрямую.
- У моделей с сэмплированием (оригинальный Chronos) отделять разброс от возмущений от собственной случайности модели (фиксировать seed, много сэмплов или использовать квантильные модели).

## Реализация этапа B (H4)

Определения — в `docs/decisions.md` (2026-11-01, «зафиксировано до расчёта»), здесь только как это устроено в коде.

- `encode_layers` (`src/models.py`): выходы блоков энкодера снимаются хуками на `encoder.block[i]` (скрытые состояния — `out[0]` у обеих моделей), берутся 32 токена патчей. Уровни: input (глубина 0), block1…blockN (i / N), final (после итоговой layer norm, глубина 1). Проверено: input и final побитово совпадают с `encode_patches`; итоговая layer norm от выхода последнего блока даёт final; у Chronos-2 прогноз из того же прохода совпадает с `predict_quantiles` до 1e-6 std контекста; S5, пересчитанный по этим эмбеддингам, совпадает с `s5.npz` до 2e-7 относительной разницы.
- Эмбеддинги на диск не пишутся (32 токена × 13 уровней × 768 на окно — десятки ГБ). `scripts/cache_localization.py` считает детекторы в том же проходе и сохраняет только счёт и τ′ для каждого уровня.
- Стоимость rbf повторяет `CostRbf` из ruptures 1.1.10: диагональ ядра равна 1. В C-реализации `KernelCPD` диагональ обрезается до exp(−0.01), поэтому сверка — с `Binseg` и `Pelt` на `CostRbf`. При равных значениях стоимости наш argmax берёт первую точку, ruptures — последнюю; на сверках расхождений не было.
- Сверки, которые скрипт повторяет при каждом расчёте и на которых падает: одно разбиение против `Binseg(n_bkps=1)` (на сырых значениях относительная разница счёта до 1e-13; на эмбеддингах Binseg получает эмбеддинги окна, посчитанного в одиночку, и разница до 1e-7 — это расхождение батча и одиночного окна в float32; τ′ совпадает везде); точный PELT против `ruptures.Pelt` при нескольких штрафах (при отладке — 0 расхождений в 48 сравнениях); окно в одиночку против батча; у Chronos-2 — прогноз из прохода против кеша (или `predict_quantiles`, если кеша прогнозов нет, как на seed 1). У Bolt прогноз в этом проходе не считается, поэтому его сверки нет. CUSUM (р4) без ограничения на края совпадает с S3.
- `OMP_NUM_THREADS=1` задаётся в начале скрипта, чтобы процессы PELT не делили ядра. torch читает эту переменную при импорте, поэтому энкодер Bolt на CPU тоже работает в один поток. Время на всём seed (второй компьютер, seed 1 / seed 0): сырые методы 308 / 269 с (PELT в 10 процессах), Bolt 665 / 629 с на CPU, Chronos-2 994 / 952 с на GPU за оба горизонта; оценка `stage5_localization` — 5 с. Файлы: `localization_raw.npz` 11 МБ, Bolt 8.4 МБ, Chronos-2 30 МБ на seed.

## Реализация каскада (H5)

Определения — в `docs/decisions.md` (2026-11-02, «зафиксировано до расчёта»), выводы — `docs/results/stage6_cascade.md`.

- `src/cascade.py`: начало обрезанного контекста по τ′ этапа B (`crop_start`), по истинной τ (`oracle_start`), reset-and-grow (`reset_and_grow_starts`); метрики окна (`forecast_metrics`); исход обрезки по разметке этапа B (`crop_outcome`); уровни этапа B каскада (`STAGE_B`).
- `scripts/cache_cascade.py` считает прогноз по обрезке каждого окна при любом счёте детектора, поэтому любые пороги этапов A и B (в том числе П2м и кривая по q) оцениваются без новых прогонов. Кроме reset-and-grow: он зависит от порога этапа B (берётся из `results/stage5/meta.json`). Одинаковые контексты (ряд, начало, конец) считаются один раз; контексты сортируются по длине, чтобы в батче было меньше дополнения NaN. На диск идут только MAE, CRPS, покрытие и ширина 80%-интервала в единицах ряда. Сверки, на которых скрипт падает: полный контекст в одном батче с обрезанными — против кеша L512; обрезанный контекст в одиночку — как в батче (порог 1e-4 std контекста).
- `scripts/stage6_cascade.py` читает кеши обоих seed. S4б и S2 считаются так же, как на этапе 4. Порог этапа B пересчитывается по seed 1 и сверяется с `results/stage5/meta.json`; проверяется, что обрезки в `cascade.npz` сняты с того же уровня и с тем же порогом. Бутстреп — веса рядов (`bootstrap_counts` этапа B); все метрики — отношения сумм по рядам, поэтому 1000 выборок считаются одним умножением матриц. log r ограничен снизу log 1e-6: при обрезке по началу залипания прогноз бывает почти точным.
- `cache_forecasts --variants` считает только часть вариантов контекста. В файле ячейки тогда есть массив `variants` (имена), в `meta.json` модели — ключ `variants`. `load_forecasts` сам переводит номера из `dataset.json` в номера файла и падает, если запрошен непосчитанный вариант. Шум S7 строится всегда, поэтому варианты не зависят от того, какие посчитаны.

## Аудит реального газового стенда (2026-11-12)

- `scripts/download_gas_data.py`: потоковая загрузка оригинального ZIP, проверка CRC, безопасная распаковка только двух ожидаемых имён без перезаписи отличающихся локальных данных. Манифест с размерами/SHA256 — `data/raw/uci_gas_dynamic/manifest.json`. SHA256 локальные, не опубликованные upstream.

Сохраняется вектор времён для точного счёта повторных меток; весь числовой файл в памяти не держится. NaN/Inf каналов учитываются, не конечные время/задания останавливают аудит с номером строки. Ничего не интерполируется/пересортировывается.
- `scripts/audit_gas_data.py`: обе записи, полные эпизоды постоянной пары заданий, события, секундные агрегаты для графиков, хвостовые изменения без порога устойчивости, геометрия окон при 100/10/1 Гц; версии и хеши кода — `results/real_gas_audit/audit.json`. Квантили длительностей/диагностики точные по соответствующим таблицам, std — популяционное по суммам квадратов (возможна малая погрешность округления). Корреляция описательная, по секундным средним. Индексация строк с нуля.
- `scripts/check_gas_audit.py`: повторная проверка исходных SHA256/CRC и хешей кода, сумм строк по независимым таблицам, границ эпизодов/событий и гистограммы времени → `validation.json`. Не доказывает физическую устойчивость.
- 10 тестов аудита + 13 тестов загрузчика; вместе с прежними 46 — 69. Новые зависимости не потребовались. Выводы/ограничения — `docs/results/real_gas_audit.md`. Команды — `README.md`. Прогнозы и сигналы S1/S4 на этих данных ещё не вычислялись.
